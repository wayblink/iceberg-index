索引层 TVF 接入方案P1 · 已确认按 A 执行

目标：把索引从“只能 CALL 的过程”变成“FROM 里的一张表”。本文同时回答三个问题：TVF 是什么、相关代码放在哪些模块、AT_OR_BEFORE 是什么意思。

一句话概括

TVF（Table-Valued Function，表值函数）是返回一张表的函数，因此可以写在 FROM 子句里，像普通表一样被过滤、投影、join、聚合。 本方案新增 3 个 TVF，内部直接调用已经写好的检索代码，不新增 optimizer 规则、不改变任何现有查询的计划。

一、TVF 是什么

1.1 与标量函数对比

种类输入输出出现位置例子
标量函数（UDF）一行一个值SELECT / WHERE 表达式里vec_distance(embedding, q)
表值函数（TVF）一把参数一张表FROM 子句FROM vector_index_search(...)
存储过程（CALL）一把参数一张表只能作为独立语句CALL system.vector_search(...)

TVF 和过程都能“返回一张表”，区别在能不能嵌进查询：

  • CALL 是独立语句，自己跑完自己输出，结果就是终点，不能再 WHERE / JOIN / 聚合；
  • TVF 是查询里的一个表来源，和其他表同等对待。

Spark 内置的 TVF 其实一直在用：range(10)、explode(arr)、posexplode、inline、stack。

1.2 接入前后对比

-- 现在（过程）：拿到结果就是终点，想再加工只能落临时表或自己解析 JSON 列
CALL spark_catalog.system.vector_search(
    table => 'db.docs', column => 'embedding',
    query => array(0.95d, 0.05d), k => 10);
-- 返回 data_file / pos / score / row(JSON)

-- 接入后（TVF）：索引结果是查询里的一张表
SELECT id, score
FROM vector_index_search('db.docs', 'embedding', array(0.95d, 0.05d), 100)
WHERE score > 0.5
ORDER BY score DESC
LIMIT 5;

-- 与业务表 join
SELECT d.id, d.body, h.score
FROM vector_index_search('db.docs', 'embedding', array(0.95d, 0.05d), 10) h
JOIN db.docs d ON h.data_file = d.__file AND h.pos = d.__pos;

-- 嵌进子查询再聚合
SELECT avg(score) FROM (
  SELECT * FROM text_index_search('db.docs', 'body', 'iceberg table', 50)
) t;

二、为什么先做 TVF（决策点 1 = A）

当前索引有三个缺口：不可组合（结果是扁平的 JSON 列，不能再过滤/join/取列）、不自动（必须显式 CALL）、无类型化契约（距离语义在适配器内部，planner 不知道）。

TVF 以最小代价解决第一个缺口：

维度TVF（P1）自动改写（P2–P4）
用户写法FROM vector_index_search(...)普通 SQL：ORDER BY vec_distance(...) LIMIT k
是否碰 optimizer否，无新规则、无代价模型、无统计依赖是：距离表达式 + 规则 + 物理计划
正确性风险低：只有显式写 TVF 的查询走索引，等价于今天的显式 CALL中高：要判断“何时敢信索引”，并处理残差与回表
检索代码零改动，直接调 VectorIndexSearch / IndexSearch复用同一底座，外加回表与残差算子
工作量小（3 个函数 + 测试）大（分期 P2/P3/P4）

而且 TVF 的检索底座正是自动改写要复用的，先做 TVF 等于给 P2 铺路，并能提前拿到真实使用反馈。

三、三个 TVF 的定义

TVF参数（位置参数）输出列内部调用
vector_index_search(table string, column string, query array<double>, k int)data_file string, pos long, score double, row stringVectorIndexSearch.search(...)
vector_index_search_batch(table string, column string, queries array<string>, k int)，每个元素是逗号分隔的数字query_id int, data_file string, pos long, score double, row stringVectorIndexSearch.search(...)（一次多查询，按命中数据文件只读一次）
text_index_search(table string, column string, query string, k int)data_file string, pos long, score double, row stringIndexSearch.search(..., "text", payloads, k)
为什么用位置参数

位置参数（'db.docs', 'embedding', array(...), 10）在所有 Spark 3.5 上都可用。命名参数（table => 'db.docs'）对 TVF 的支持随版本而变，实现时若确认可用再开放，否则一律位置参数，行为一致。

3.1 为什么批量向量查询用 array<string>

Spark 的 CALL/TVF 参数不接受嵌套数组字面量（array(array(...)) 解析失败），所以批量查询和现有 vector_search_batch 过程保持一致：每个查询是一个逗号分隔的数字字符串。

四、模块放置（决策点 2，附现状盘点）

顾虑是“Iceberg 会不会因此堆进太多计算/索引相关的东西”。先看现状——索引相关代码已经按职责分在四个层次，向量计算是独立的：

iceberg-api 公共接口（暂无索引类；IndexCatalog 未来作为 SPI 进这里） iceberg-core org.apache.iceberg.index.* ← 引擎无关、类型无关的索引层 IndexFile / IndexManifest / IndexSnapshot / IndexMetadata IndexBuilder / IndexRefresher / IndexReader / IndexCatalog IndexTypes 注册表 / Puffin 容器 / IndexAdapter 抽象 （无任何 ANN、无 BM25、无 Spark 依赖） iceberg-index-vector org.apache.iceberg.index.vector.* ← 向量检索的“计算”都在这里 VectorIndexAdapter（EXACT / HNSW、jelmerk hnswlib、精确重排） VectorIndexDefinition / VectorIndexType / VectorIndexTypes 唯一引入 hnswlib 依赖的模块 iceberg-index-text org.apache.iceberg.index.text.* ← BM25 的“计算”都在这里 TextAnalyzer / TextIndexAdapter（自实现 BM25，无 Lucene） TextIndexDefinition / TextIndexType / TextIndexTypes iceberg-spark (3.5) org.apache.iceberg.spark.index.* ← 引擎适配层（类型无关） IndexEntries（删除感知的通用条目流水线） SparkIndexBuilder / IndexGrouping / IndexSearch / VectorIndexes org.apache.iceberg.spark.procedures.* ← SQL 过程外壳 iceberg-spark-extensions SparkProcedures 注册表 + 各过程测试 【本方案新增】3 个 TVF

依赖方向：spark → index-vector / index-text → core → api；core 不反向依赖任何适配器模块，也没有任何向量或文本计算。

结论：

  • 向量检索相关的东西已经有专门模块 iceberg-index-vector（HNSW 图构建、量化、距离度量、重排全在里面），core 只有抽象；BM25 同理在 iceberg-index-text。
  • Spark 侧的 org.apache.iceberg.spark.index 是类型无关的引擎适配（条目生成、构建、刷新、检索、行解析），不包含距离或 BM25 的计算实现。
  • SQL 面（过程、以及本方案的 TVF）放 spark-extensions：这是 Iceberg 已有的“SQL 扩展”模块，本就承载过程注册与自定义函数，不新增模块、不污染 core。
  • P2 的距离表达式 vec_distance 也放 spark-extensions——它的语义必须与索引的 metric 绑定（同列 COSINE 与 EUCLIDEAN 给出完全不同的距离），只有 Iceberg 侧知道该用哪个索引、哪种度量，Spark 官方 ML 函数无法感知索引。

五、AT_OR_BEFORE 是什么（决策点 3）

5.1 你的理解是对的

“索引可以覆盖一部分数据时仍然可用：索引用在它覆盖的部分，没覆盖的部分走暴力扫描，最后合并。” —— 这正是 AT_OR_BEFORE 的语义。

5.2 两种一致性模式

模式语义索引快照落后于读快照时
EXACT_SNAPSHOT（默认）必须存在绑定到恰好该表快照的索引快照报错 / 回退全表扫描
AT_OR_BEFORE取绑定表快照 ≤ 所查快照的最新索引快照用旧索引 + 补齐差额

5.3 机制：差额从哪来

读快照 S（表的最新快照） │ ├─ 索引最新快照 I，绑定表快照 S' ≤ S │ ├─ I 覆盖的数据文件集合 C（来自 I 的 manifest） │ ├─ 差额 = S 的数据文件 − C │ └─ IndexReader.uncoveredDataFiles(query, S 的数据文件) 直接给出这个集合 │ ├─ 已覆盖部分：driver 侧检索 I → (data_file, pos, score) └─ 差额部分：普通扫描 + 同样的打分 → (data_file, pos, score) │ └─ 合并 → 去重 → 全局 TopK

纯追加场景（你举的例子）下差额就是新写入的数据文件，旧文件一条没动，索引结果完全有效，只是少了新数据——补一次暴力扫描即等价于全表。

5.4 一个必须注意的细节：删除

如果“落后”不只是追加，还包括对已覆盖数据文件的删除，那么索引命中就不能直接用了：

  • 位置删除（position delete）加在某个已覆盖的数据文件上 → 索引里仍留着那些位置的条目，指向已被删除的行；
  • 等值删除 / 文件重写 → 数据文件换名，变成“新文件”，自然落入差额集合，这部分是安全的。

所以 AT_OR_BEFORE 的正确读法必须是两步：① 差额文件暴力扫描；② 索引命中还要按当前快照的删除文件过滤一遍（位置删除的 (file, pos) 检查很便宜）。这一步属于 P3 残差扫描的实现内容，本方案（P1）不涉及，但必须记在账上。

5.5 为什么文本侧更保守

BM25 分数依赖全库统计量 N 与 avgdl，而索引文件里存的是本地统计、查询时才合并（D10′ 的设计）。索引落后时合并出的统计与全表真实值有偏差：排序基本仍可用，但分数绝对值不再精确，对“按分数阈值过滤”的查询会出错。因此文本侧默认只走 EXACT_SNAPSHOT，向量侧允许 AT_OR_BEFORE + 残差（向量检索本身就是近似的，且距离值与索引新旧无关）。

六、本方案不改变什么

  • 不新增 optimizer 规则、不改任何现有查询的物理计划（没有 TVF 的查询一行都不变）。
  • 不改 core 的任何接口：TVF 只是换一个入口调用已有的 VectorIndexSearch / IndexSearch。
  • 不改现有过程：CALL 全部保留，行为不变。
  • 不引入新的第三方依赖。

七、已知限制（本期接受）

  • row 仍是 JSON 字符串列。要变成类型化的 id、body 列，需要“按 _file/_pos 回表取列”的物理算子，属 P3。当前可用 get_json_object(row, '$.id') 自行解析。
  • 只维护 Spark 3.5（4.1 已不在维护范围）。
  • TVF 内部仍走“driver 侧检索 + 每命中数据文件读一次”的现成路径，未做分布式检索（索引文件小，无必要）。

十、验收标准（P1）

  1. 3 个 TVF 可注册、可查询，位置参数形式可用。
  2. 每个 TVF 的结果与对应 CALL 过程逐行一致（同一索引、同一参数）。
  3. TVF 结果可用于 WHERE / ORDER BY / LIMIT / 子查询 / JOIN。
  4. 没有 TVF 的现有查询计划不变（可用 explain 对比断言）。
  5. 全部既有索引测试保持通过（core / index-vector / index-text / spark / spark-extensions）。
