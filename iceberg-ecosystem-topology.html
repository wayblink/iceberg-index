Iceberg 向量湖仓生态粗粒度拓扑

从系统边界看 Spark、Iceberg、Index Layer、Lance、S3 与向量执行引擎如何共同工作。这里刻意隐藏 index layer 的内部类和文件结构，只保留可以指导项目分工、部署和 POC 的组件级视图。

图的阅读口径 Iceberg：表和版本的权威控制面。 Index Layer：与 Iceberg snapshot 对齐的派生检索层。 Lance：向量数据/索引段格式的候选物理层。 FAISS / Knowhere：向量检索执行引擎，不是 Catalog。 更新时间：2026-09-18

一句话定位

应用把查询交给 Spark；Spark 通过 Iceberg Catalog 读取表的权威版本，通过 Index Layer 判断是否有可用向量索引；向量引擎负责候选召回，结果再回到 Iceberg 表数据完成过滤、权限、删除语义和最终行读取。S3 承载这些表数据、元数据和索引文件。

最重要的边界

不要把 “Lance + FAISS/Knowhere” 误画成 Iceberg 的替代 Catalog。建议把 Lance 放在派生的向量数据/索引段位置，把 Iceberg 放在表身份、快照和可见性的位置。

一、整体生态拓扑

查询与消费平面 元数据与控制平面 数据与索引平面 对象存储平面 可选或待验证组件

粗粒度图只表达组件之间的职责和主路径：Spark 是计算/查询与构建入口，Iceberg Catalog + Table Metadata 是表权威，Index Layer 负责索引与表 snapshot 的协同，Lance 和向量引擎属于派生的向量访问路径，S3 承载所有持久化文件。

二、两条最重要的业务路径

READ PATH · 查询

应用 → Spark → 索引候选 → Iceberg 回表

应用提交 SQL 或检索请求，Spark 负责执行。查询适配层先看当前 Iceberg snapshot 是否有匹配的索引版本；如果有，向 FAISS/Knowhere 等引擎取候选，再依据行身份回到 Iceberg 行数据完成过滤、删除语义和结果投影。索引未覆盖的文件仍需走 fallback，不能默认“有索引就全表安全”。

BUILD / REFRESH PATH · 构建

Iceberg snapshot → Spark 构建 → Lance/索引段 → 发布

构建作业从指定 Iceberg snapshot 读取行数据和向量，使用向量引擎生成索引产物，以 Lance 或其他格式写入 S3，校验覆盖范围和版本绑定后，再把新索引版本发布到 Index Layer。表发生追加、删除、重写或快照过期时，索引必须进入 refresh、重建或回退流程。

三、组件职责：谁负责什么，谁不负责什么

组件主要职责不应承担的职责在本项目中的定位
应用 / API / BI发起 SQL、相似度或混合检索请求，消费最终结果。不直接拼装 S3 路径或判断索引版本。业务入口。
Spark查询执行、批量构建、refresh、回表和结果计算。不替代 Catalog，也不等于向量索引算法。首选计算与编排引擎。
Iceberg Catalog + Table Metadata管理表身份、当前元数据、snapshot、manifest 和数据文件可见性。不负责 ANN 候选召回。表的权威控制面。
Iceberg Index Layer登记索引版本、覆盖范围，并把索引安全地绑定到表 snapshot。不替代 Iceberg 表，也不直接成为向量执行器。表之上的派生控制面。
Lance承载向量列、向量批次或索引段的物理数据格式。不天然提供 Iceberg Catalog 的表版本权威。建议作为向量 sidecar / serving data format。
FAISS / Knowhere / 其他执行 exact 或 ANN 搜索，返回候选 ID 和分数。不负责业务字段过滤、删除语义和最终行读取。可替换的向量执行后端。
S3持久化 metadata、manifest、表数据、Lance 数据和索引产物。不决定哪个 snapshot 对用户可见。统一对象存储层。

四、Lance 在生态中的两个落位选择

推荐 POC · DERIVED SIDEcar

Iceberg 做权威表，Lance 做向量访问层

Iceberg 继续管理业务行数据、schema、snapshot 和 delete/rewrite 可见性；Lance 存向量列或索引段，通过 row identity 和 source snapshot 与 Iceberg 对齐。这个方案更符合“索引是派生层”的定位，也方便 Spark 回表和未覆盖 fallback。

需要额外协议 · PRIMARY VECTOR DATASET

Lance 作为向量主数据集

如果希望 Lance 直接成为向量主数据格式，就必须补一层 Iceberg↔Lance bridge：统一 row identity、快照版本、删除/重写传播、权限和回表映射。否则会出现向量检索返回了结果，但 Iceberg 当前 snapshot 已经看不到对应行的问题。

五、建议的项目边界

PHASE 1 · 打通主链路

Spark + Iceberg + S3 + exact vector engine

先让 Spark 能从 Iceberg snapshot 读数据、调用一个向量后端、根据 row identity 回表，并把索引版本安全写到 S3。Lance 可以先作为向量段格式，但不急于同时支持多个后端。

PHASE 2 · 形成可替换生态

Index Layer + Lance + engine adapter

把 FAISS、Knowhere 或其他引擎放到统一 adapter 后面，补齐 refresh、覆盖范围、delete/rewrite 和 fallback。此阶段验证 Lance 是否适合承载长期索引段和向量列。

PHASE 3 · 生产化查询

混合检索、服务化和多引擎

再接 BM25/结构化过滤、reranker、GPU/磁盘索引、缓存和低延迟 serving。Spark 仍可作为批量构建与回表引擎，在线查询可按延迟要求增加专用服务。
