## 查询：同窗口对照（2026-11-23，两腿交替跑，本节取代下面的跨窗口数字）

窗口 02:30–03:40 UTC，同一张表、同一份语料、同一查询集，两侧各 12 executors × 4c/16g + 12g driver；v1 用基线提交 `d16bcbe3b6` 构建的 "v1 writer" 镜像（同一套注册表代码、只写 v1 payload），v2 用本分支镜像。两腿之间用 `drop_index(purge => false)` 切换（4.5 分钟）。

| 索引总量 | 12,613,433,075 B / 1,170 B/行 | **2,309,837,741 B / 214 B/行** | **5.46×** |

**结论修正**：v2 以 **5.46× 体积、1.61× 构建速度**，换来 **约 1.6× 的查询 CPU**（每查询 warm-min 慢约 1.5×）。这不是噪声：两腿 task 数完全相同（4,200 = 20×5×42），task 时长却差 1.58×，且长尾样本比例一致（14 vs 13），说明差异来自索引读路径而不是集群抖动。原因在结构上：v1 的每条 posting 自带行引用，查询只读命中词的范围；v2 的 posting 只有 `(docId, tf)`，每个命中文档还要读**文档表分块**并做多路归并，常见词会命中大量分块。follow-up：#3188（文档表块缓存/紧凑解码）。

下面的跨窗口数字保留作历史记录，**不可用于比较**：v1 来自 11-20 的独立窗口（p50 3,256），v2 来自 11-20 的另一窗口（p50 3,132）。当时的"v2 略快"是同窗口对照下站不住的结论，以本节为准。

## 复核：11-20 的 v1 索引里超长词项是被截断的（2026-11-23）

今天在同一张表上重跑 v1，构建失败在 `TextIndexPayload.encode` 的 `dictionary.writeUTF(term)`：

```
java.io.UTFDataFormatException: encoded string (hooooo...oooo) too long: 94065 bytes
```

语料里存在一个 **94,065 字节的 token**（同一字符的长串），而 v1 的词典用 Java `writeUTF` 写词项，上限 65,535 字节。

**11-20 为什么能建出来**：不是老代码能装下长词。当时构建器写 entry payload 的 token 长度用 `writeShort`（u16），`94,065 & 0xFFFF = 28,433` 字节——超长 token 被**静默截断**成另一个更短的词，v1 的 `writeUTF` 从未见过超限串。后来 v2 的工作把 `encodeTokens` 的 u16 改成 32 位长度并加了回归测试；今天用带该修复的代码跑 v1 编码器，完整 token 才撞上上限。

证据链：
1. 11-20 的镜像里反编译 `TextIndexPayload.encode`，词典写入同样调用 `writeUTF`（不是 32 位长度）；
2. 同一镜像的 `TextAnalyzer` 反编译后没有任何词长上限；
3. 11-20 构建记录的 `source_snapshot_id = 3615081701212041418` 与当前快照一致，586 个数据文件 / 83.38 GB / 10,784,907 行都未变；
4. 失败字符串是纯字符长串，符合"被 u16 截断后仍超过 20 KB"的特征。

含义：**11-20 那个 12.6 GB 的 v1 索引里，这类超长 token 的词项是错的**（存的是截断后的词），拿它做召回或体积对比会低估 v1 的实际语义；并且 **v1 布局本身装不下这类词**。收敛时 "v1" 这个名字必须落在 v3 的布局上（32 位长度写字符串），不能退回历史 v1 布局。为完成同窗口对比，临时把 v1 词典改成 32 位长度（posting 与行引用布局不变），该改动只存在于开发分支，收敛时删除。

## 可比性（必须写清）

- **体积是硬数字**：两次独立的 v2 构建（11-20 与 11-23）逐对象字节完全相同（2,309,837,741 B），v1 也两次都是 12,613,433,075 B——与负载无关。
- **构建**：11-23 同窗口里 v1 805,580 ms、v2 499,170 ms（1.61×）；该窗口比 11-20 干净窗口慢约 30%（v1 619,358 ms），所以绝对耗时含负载，只有**同窗口比值**可用。
- **查询**：11-23 窗口有严重 IO 长尾（p95 66–94 s、单样本最长 196 s，>10 s 样本各约 14/100），绝对值不可比；可用的量是**每查询 5 次里最好的一次**与**task 总时长**，前者对停顿稳健、后者按 task 数归一（两腿 4,200 个 task 相同）。
- **查询的 p50 差异（-4%）在运行间噪声内**（#3174 记录同一配置四次运行 p50 摆动 ±10%），不能给倍数。p95/max 的下降（9.5 s→5.9 s、52 s→24 s）方向明确但同样混着窗口差异，只作参考。
- 本轮查询窗口在集群工作时间，未与其它大作业刻意错开（v1 那轮是独立窗口）；严格对照需要同一窗口交替跑两代索引，本轮没做。
