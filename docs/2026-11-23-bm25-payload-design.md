# BM25 索引 payload 设计（单一布局：文件表 + 长度列 + posting）

状态：已收敛。此前存在三种布局（逐条行引用的 v1、按 4096 文档分块的 v2、长度列的 v3），2026-11-23 起只保留第三种；它的 payload 格式版本为 **2**（blob 类型 `iceberg-text-bm25-v1`、payload magic `0x424D3102`、`FORMAT_VERSION = 2`、readerId `text/bm25/2`）。版本号写在 payload 签名的低字节，与向量 kernel 的 `payloadFormatVersion` 同一规范；blob 类型只标角色，不随版本变。旧两种布局的代码与读路径已删除，不做向后兼容。

## 升级

版本 1 写出的文本索引在本版不可读：查询和刷新都会明确报 `Unsupported BM25 payload format version: 1 (this build reads 2); rebuild the index`，`CALL system.check_indexes` 会把它们报成 `readable => false` 并给出重建语句。迁移不能靠 `refresh_text_index`——刷新沿用父快照的分片，旧 payload 不会被重写；必须先 `CALL system.drop_index(table => '...', column => '...', index => '<uuid>', purge => true)`，再 `CALL system.build_text_index(table => '...', column => '...')`。

## 1. 目标与约束

- 索引体积要小：旧布局 11.75 GiB（1,169 B/行，10.78M 行）里 96.58% 是 posting，每条 posting 8.25 B，其中绝对行号 4.29 B、每条长度 1.79 B、数据文件路径 2.53 B。
- 查询要正确：top-k 与旧布局逐位一致，BM25 的 idf 与 `(k1+1)` 口径不变。
- 不做有损近似、不加用户可调参数、不改引擎（`readableAuxiliaryBlobTypes()` 保持不变）。

## 2. 最终布局

一个索引文件是一个 Puffin 辅助 blob，blob 内按顺序排列：

1. **header**（308 B）：magic、文档数、token 总数、文件数、各段长度、词典起点、posting 起点、64 个词典桶的偏移。
2. **文件表**：每个数据文件的 `(路径, 该文件第一条文档的 docId, 该文件第一条文档的行号)`。
   - 索引文件覆盖的数据文件按行顺序排列，同一个文件内行号连续，所以任一文档的行号 = `rowStart + (docId - docStart)`，**不需要逐文档行引用**。
   - 数据文件不连续（A、B、A 这种顺序）在编码时直接拒绝；文件内有空洞时用"行例外表"记录少数不连续的 `(docId, 行号)`。
3. **长度列**：每个文档一个 `uint16`（小端），整列 zlib 单流压缩；长度 ≥ 65535 的文档写哨兵并在溢出表里记真实值。查询只需要这一列，一次 range 读就能拿到整个分片的长度，不再按块读文档表。
4. **行例外表**（默认为空）：varint 的 `(docId 增量, 行号)`。
5. **词典**：64 个桶，桶内词项前端编码（共享前缀 + 后缀），每项写 `(df, 该词 posting 区间相对桶内上一项的偏移增量, 区间长度)`。
6. **posting**：每个词的 posting 区间独立 zlib 压缩，内容只有 `(docId 增量, tf)` 的 varint 流。统计文件复用同一布局（文档数为 0、无长度列、空 posting 段）。

## 3. 为什么是这个布局（三次实测）

| 布局 | 体积 | 查询 task 总时长（20 查询 × 5 次） | 说明 |
|---|---:|---:|---|
| 逐条行引用（旧 v1） | 12,613,433,075 B / 1,169 B/行 | 3,767 核秒 | posting 自带路径与行号，读放大最小但体积最大 |
| 文档表分块（v2） | 2,309,837,741 B / 214 B/行 | 5,866 核秒 | 体积 5.46× 小，但每条查询要把整张文档表读一遍（每分片 245 次 range read、3.79 MB），查询 CPU 回退 1.58× |
| **长度列（当前）** | **2,284,617,255 B / 212 B/行** | **4,852 核秒** | 文档表只剩一列长度，每查询按一次 range 读；相比分块文档表查询 CPU −17.3%、体积 −1.09%，答案逐位一致 |

体积与查询的权衡是设计核心：路径与行号的 6.8 B/条 posting 是体积的主要来源（去掉后 5.46×），但"去掉之后怎么找回行号"决定了查询成本——按块存文档记录会读放大 2.8–311×（df 越大放大越小），按列存长度只读一次、行号靠文件表算，是两者的交点。

## 4. 被否的方案

- **posting 内联 `(fileId, 行号)` varint（v2a）**：约 3.37 B/posting、总量 5.05 GiB，体积 2.3×，只在长度列方案达不到查询目标时才考虑。
- **块内帧对齐/更小块**：只降低解压粒度，不减读取字节数，且压缩率变差（+3–15%）。
- **只调大块大小**：请求数变少但字节不变，属于缓解。
- **缩小分片内块尺寸**：文档按 docId 均匀分布，任何 df ≳ 3,000 的词几乎命中每个块，块级跳过失效。

## 5. 顺带修掉的既有缺陷

- 入口 token 长度用 16 位写，超过 65,535 字节的 token 被静默截断成另一个词（历史 v1 索引里确实存在这种坏词项）。
- 旧 v1 词典用 `writeUTF`，语料里 94 KB 的 token 会直接让构建失败（`UTFDataFormatException`）。新布局用 32 位长度写字符串。
- 统计文件与数据分片共用布局，省掉一套解析代码。

## 6. 已知代价与后续

- 查询 CPU 仍高于旧 v1 布局（4,852 vs 3,767 核秒，1.29×）：长度列每次查询要解压整列。跟进卡 #3192（读路径缓存/块化长度列）。
- 构建比 lance-spark 的原生 FTS 慢约 15×（同一窗口 377,935 ms vs 24,624 ms），索引体积是对方的一半（2.13 GiB vs 4.21 GiB）。构建差距的归因另立卡。
- 10M 实测：构建 375,803→377,935 ms 量级、体积 5.46× 小、top-1 20/20、top-10 重叠 1.000。

## 7. 验收口径

- top-k 与旧布局逐位一致（同一查询集、同一统计口径）。
- 体积按 S3 逐对象字节统计，B/行以表行数为分母。
- 查询按"同窗口、两腿交替、task 总时长 + 每查询 warm-min"报告，不用跨窗口数字下结论。
