# 索引的增量构建与补建

日期：2026-11-23　分支：`card/3170`（基底 `index`）　适用：向量索引

这份文档只讲两件事：**表发生变化之后，如何只重建受影响的部分**（增量构建），以及**索引没盖满整张表时，如何只把缺的那部分补上**（补建）。

两者的入口是同一个命令 `refresh_vector_index`，但触发条件、读到的字段含义、留下的历史都不同，混着理解很容易得出错误结论。先看下面这张表。

## 0. 一页看清

| | 增量构建 | 补建（同源补覆盖） |
|---|---|---|
| 想解决 | 表写入/删改/重写后，索引落后了 | 索引没盖满当前的表快照 |
| 触发条件 | 索引最新版的源表快照 ≠ 当前表快照 | 索引最新版的源表快照 = 当前表快照，且有数据文件没被覆盖 |
| 重建什么 | 新增的数据文件；内容变过的数据文件（含它所属的组） | 只有没被覆盖的数据文件 |
| `source_snapshot_id` | 变成新的表快照 ID | 不变 |
| `index_snapshot_id` | 前进一格 | 前进一格 |
| 旧的那版索引 | 保留在历史里，新版本以它为父 | **被替换掉**，同一份表快照始终只有一版 |
| 和 `PARTIAL` 的关系 | 无关 | 由一次部分构建的 `PARTIAL` 报告引出 |

两者在**同一次调用里互斥**：一次 `refresh_vector_index` 要么在做增量，要么在补建，不会同时做两件事。原因是判据本身互斥——"索引最新版针对的是哪份表快照"只可能有一个答案。

## 1. 增量构建

### 1.1 什么时候用它

索引是绑定表快照的，不自动跟随写入（见用户手册 3.4）。表的当前快照变了，索引就落后：改写查询会继续用旧索引的答案加上对未覆盖文件的补扫，答案往往仍然对，但索引的价值在下降。跑一次 refresh 把它追上：

```sql
CALL local.system.refresh_vector_index(table => 'db.docs', column => 'embedding');
```

它总是针对**当前**表快照，没有"指定某个历史快照"的参数。

### 1.2 到底重建了什么

refresh 把旧索引覆盖的数据文件集合，与当前表快照的数据文件集合做差，再看两类"同名但内容变了"的情况。四类数据文件四种处理：

| 数据文件的情况 | 怎么判定 | 处理 |
|---|---|---|
| 新增 | 在当前快照里有、旧索引没覆盖 | 编入新组，正常重建 |
| 被删除 | 旧索引覆盖了、当前快照里没有 | 不重建（没数据可建），但它所在的组要重建——索引文件不能只重写一部分 |
| 内容变了 | 新旧快照都有，但**删除文件**集合不同 | 所在的组整体重建 |
| 没变 | 新旧快照都有，删除文件也相同 | 原样复用，不读数据 |

"内容变了"只认删除文件这一个信号，不是比对数据文件的字节。原因很实际：判断一个数据文件的内容是否变化需要读它，而增量构建的全部价值就是不读没变的文件。**`INSERT OVERWRITE` 或 `rewrite_data_files` 会写出新的文件名**，旧名字消失、新名字出现，在上表里分别落进"被删除"和"新增"两行，所以这类改写天然被覆盖。真正需要靠删除文件判定的是 `MERGE`/`DELETE`/`UPDATE`：数据文件不动，新增一个删除文件，那些行必须从索引里消失。

### 1.3 组的放大效应（最容易踩的坑）

索引的最小单位是**组**：一个索引文件覆盖一组数据文件（`max_entries_per_index_file` 控制一组装多少条目）。索引文件不能局部重写，所以**一个数据文件的内容变了，和它同组的所有数据文件一起重建**。

这有两个后果：

- 重建成本按"组的规模"算，不按"变化的文件数"算。1 个文件变化可能触发 100 万个条目的重建。
- `max_entries_per_index_file` 不只影响构建时的并行度，也决定了后续每次增量的最小重建粒度。默认 100 万条目会把大量小文件并成一组，增量就变得很粗。表很宽、很多小文件、又频繁增量时，把预算调小能让增量更细，代价是索引文件更多、HNSW 图更碎（召回略降）。

反过来，如果表基本是"整批重写"的模式，预算调小并不能省什么——每批数据都换了文件名，重建量本来就等于全量。

### 1.4 什么都没变的时候

对同一张表连续跑两次 refresh，第二次不会做任何事：索引已经针对当前表快照且覆盖完整，函数直接返回，**不产生新的索引快照**，输出 `index_files = 0, entries = 0`，`list_indexes` 的 `index_snapshot_id` 停在上一次的值。

这是判断"我的 refresh 到底做了没有"的唯一可靠信号：看输出是不是 0。

### 1.5 表快照变了但数据没变

有一种中间情况：表产生了新快照，但数据文件一个没变。典型来源是只重写 manifest（`rewrite_manifests`）、或者只改了表属性而 Iceberg 仍然提交了新快照。

这时三类差异都为空，refresh 会发布一个**重新指向**的索引快照：索引文件一个都不重建、直接复用，只是把源表快照改成新的。输出的 `index_files` 是复用的文件总数，**不是 0**。

所以"0 表示没做事"要理解准确：0 表示连重新指向都不需要（索引已针对当前表快照）；非 0 不等于"重建了这么多文件"，见下一节。

### 1.6 输出怎么读

```sql
index_uuid | source_snapshot_id | index_files | entries
```

- `index_files` / `entries` 是**发布出来的那版索引的总量**，不是"这次重建了多少"。一次增量只重建 1 个文件、但索引一共有 40 个文件时，这里报 40。
- 这两个数是 0 主要有两种情况：索引已经完整针对当前表快照（什么都没做），或者并发下另一个发布者先赢了（见第 4 节）。还有一种边角来源：表快照里已经没有数据文件（行被删光），索引自然也是空的。
- 想看"这次到底重建了什么"，输出里没有。可以看 driver 日志里 `re-indexes N data files whose contents changed` 那行，或者对比新旧两版索引的 manifest。

## 2. 补建（同源补覆盖）

### 2.1 什么时候用它

"索引存在、但没盖满当前表快照"这个状态，主要来自**一次部分构建**：某组数据建不出来，其余照常发布，报告是 `PARTIAL`（用户手册 6.1）。缺口不是异常状态——覆盖是文件级的属性，索引在任何时候都可能只盖住一部分，查询靠补扫兜底。

要紧的是别把它和"索引落后"混为一谈：落后是源表快照对不上，用增量构建；缺口是源表快照对得上但没盖满，用补建。两者判据不同，见第 0 节。

`check_indexes` 会明说这件事：

```sql
CALL local.system.check_indexes(table => 'db.docs');
-- uncovered_data_files > 0，suggestion 里会给出补齐用的 refresh 语句
```

### 2.2 它做什么

refresh 发现"索引已经针对当前表快照，但覆盖不全"时，把旧的那一版当作基线，只重建**没被覆盖**的数据文件，然后用结果**替换**同一份表快照上的那一版索引。

替换这一点对用户是可见的：

- `list_indexes` 里这份表快照仍然只有一行，`index_snapshot_id` 前进一格，`source_snapshot_id` 不变。
- 不会出现"同一份表快照两版索引"、让查询或 EXACT 一致性去挑。
- 历史不会被反复补建撑大：补 5 次也只有一版。

反过来，如果索引**已经**覆盖完整，第 1.4 节的短路生效，什么都不做。

被替换掉的那一版索引文件，如果不再被任何保留的索引快照引用，就由 `cleanup_index_files` 回收（用户手册 3.4）。补建不自动清理——它只写不删，和构建一样。

### 2.3 前提：缺口的原因得先消失

`refresh_vector_index` 是**严格路径**：它不隔离失败组。缺口还在时重跑，它照样去建那批文件，照样失败，报错和上次一样。

所以顺序永远是"先处理原因，再 refresh"。原因至少分两类，处理方式不同：

| 缺口原因 | 怎么处理 |
|---|---|
| `dimension` 与数组实际长度不符 | 修数据（修正/删除/重写那批文件），再 refresh |
| `payload` 超限（相对索引预算说的大小） | 换成**更小的** `max_entries_per_index_file` 重建——refresh 继承同一个预算，原样重跑会再次超限 |

第二条容易被忽略：它不是"数据坏了"，而是"这批数据在当前的预算下装不进一个索引文件"。重跑多少次都一样。

### 2.4 补建不能跨越表回滚

refresh 只接受"当前表快照是索引最新版源快照的后代或同一份"。如果表被**回滚**到更早的快照（`rollback_to_snapshot`），当前快照不再是索引源快照的后代，refresh 会直接拒绝：

```
Cannot refresh the index of table … from table snapshot X:
it is not a descendant of table snapshot Y, which the newest index snapshot was built from
```

这时正确的做法不是反复重试，而是按回滚后的表快照重新构建（或用被回滚掉的那版索引另作打算）。之所以拒绝，是因为增量与补建都建立在"向后追加历史"的假设上，对一份更早的表快照去"增量"没有可靠语义。

## 3. 成本模型

一次 refresh 的成本 ≈ **需要重建的那些组的数据量**，与"这次新增了几个文件"关系不大。

- 全部数据都是新文件名（整批重写）：等于全量重建，refresh 不省时间。
- 少量文件新增、没有删除文件、没有数据文件被删：只建这些新文件的组，最省。
- 一个数据文件出现删除文件：它所在的组整体重建。
- 一个数据文件被删：它所在的组整体重建（去掉它）。

推论：想让增量划算，关键是让**组尽量贴合"一起变化"的单元**。表和写入模式决定了大半，`max_entries_per_index_file` 是唯一能调的旋钮。

## 4. 并发与一致性

同一份表快照最多一版索引，这是读取路径依赖的不变式，也是补建选择"替换"而不是"追加"的原因。

两个 refresh 同时跑时：

- 发布走的是元数据 CAS。后落地的那个会在**当时最新的元数据**上重放自己的变更，所以不会把对方的结果覆盖成"丢了一版"。
- 同源补建的替换请求，如果发现已经有更新的一版索引（`latest` 不是它要替换的那版），会被丢弃，输出 `index_files = 0, entries = 0`。
- 也是因为这个，**看到 0 不一定是"表没变"**——也可能是另一个发布者先赢了。要区分就看 `list_indexes` 的 `index_snapshot_id` 是否已经前进。

一个已经发布出去的索引快照，其索引文件可能被多个索引快照引用（增量复用、重新指向都如此）。因此 `cleanup_index_files` 只删"没有被任何存活快照引用"的文件——它不会因为某个索引快照过期就删掉仍被别的快照引用的文件。

## 5. 文本索引为什么不在这套能力里

BM25 要求索引**完整覆盖**查询快照才能绑定：部分覆盖的倒排绑不上，全局语料统计也会偏。所以文本索引不参与部分构建，也不参与补建，仍是"整次成功才发布"。`refresh_text_index` 存在，但它只做增量，不补缺口；且它的失败不回滚注册（用户手册 5.5）。

在向量上可以"先发布再补"，在文本上当前不行。

## 6. 操作手册

### 6.1 一次构建是部分成功之后

```sql
-- 1. 确认状态与缺口
CALL local.system.index_build_status(table => 'db.docs');
--   state = PARTIAL，error 里有原因和前几个缺口文件路径
CALL local.system.check_indexes(table => 'db.docs');
--   uncovered_data_files 才是"漏了多少个数据文件"

-- 2. 按原因处理：维度不符 → 修数据；payload 超限 → 换小预算重建

-- 3. 补建
CALL local.system.refresh_vector_index(table => 'db.docs', column => 'embedding');

-- 4. 验证缺口为 0
CALL local.system.check_indexes(table => 'db.docs');
```

第 3 步的输出如果是 `index_files = 0`，说明第 2 步没生效（原因还在，或索引已经完整），回去复查。

### 6.2 日常跟随写入

```sql
CALL local.system.refresh_vector_index(table => 'db.docs', column => 'embedding');
```

按写入频率定期跑即可，没有"增量窗口"之类的参数。跑之前不需要记上次跑到哪，它自己比对当前表快照。

### 6.3 判断一次 refresh 有没有用

| 观察 | 含义 |
|---|---|
| 输出 `index_files = 0, entries = 0`，`index_snapshot_id` 没变 | 表没变且索引完整，什么都没做（或表里已无数据文件） |
| 输出 `index_files = 0, entries = 0`，`index_snapshot_id` 前进了 | 并发的另一个发布者赢了，本次结果被丢弃 |
| 输出非 0，`index_snapshot_id` 前进，`source_snapshot_id` 变 | 增量构建 |
| 输出非 0，`index_snapshot_id` 前进，`source_snapshot_id` 不变 | 补建 |
| 抛 `not a descendant of` | 表被回滚过（2.4） |

## 7. 限制清单

- 只能针对**当前**表快照，不能指定历史快照做增量或补建。
- 表被回滚到索引源快照之前时，refresh 拒绝执行（2.4）。
- 重建粒度是组，不是文件；`max_entries_per_index_file` 是唯一的调节手段。
- 输出只报总量，不报本次增量；要精确知道重建了什么只能看日志或对比 manifest。
- 严格的 refresh 不会把"个别文件建不出来"降级成缺口——它就是要失败。想拿到部分结果，用 `build_vector_index`（用户手册 6.1）。
- 文本索引不参与（第 5 节）。
- 索引文件与表快照的生命周期独立：`expire_snapshots` 不会回收索引文件，得靠 `cleanup_index_files`（用户手册 3.4）。
