## 2. 我方撤回与修正

### 2.1 第 1 条：从"现网未触发"改为 P1

我首轮只核了 SQL 改写（`ORDER BY ... LIMIT`）这条入口，漏了表函数可以直接指定列序。`search(...)` 的 `columns` 是声明过的可选参数（`IndexTableFunctions.scala:141-146`），绑定层 `selected = if (columns.isEmpty) relation.output else columns.map(columnOf)`（同文件 `:190`）保留用户写的顺序，`TextSearchSource.scala:135` 再把这个顺序原样作为 `rowsAt` 的 `columns`；`fetchPlan`（`IndexEntries.java:827-831`）却用表序投影配请求序的 `rowSchema`。所以 `search(t, 'q', array('body'), 10, columns => array('b','a'))` 这类调用在真实表上会串值。结论接受 P1，修复需带 SQL 端到端逆序用例。

### 2.2 第 2 条：9 次即触发，我此前的"需 10 次"作废

我按"删除版本 D 本身是否出窗"计算，忽略了**证据在 D−1**：D 已经不含目标 UUID，能证明它曾被注册的是 D 之前的版本。`namedInHistory` 从当前版本起走 `VERSIONS_TO_KEEP = 10` 步，k 次后续注册时最远走到 `v(D+k-9)`；要够到 `v(D-1)` 需要 `k ≤ 8`。所以 8 次仍拒绝恢复，9 次起恢复，与 codex 的三组实验（8/9/10）一致。我方撤回步数修正，接受 P2。

### 2.3 第 9 条：竞态窗口不是毫秒级，接受 P2

我按 procedure 里"名称检查 → 生成 UUID → createIndex"之间的代码行数估算窗口，但 `createIndex` 自身就是 I/O：先 `readIndexUuids` 和 `readMetadataFile` 两个远程读（`SidecarIndexCatalog.java:172-173`），`register` 写 metadata root（`:518`）、再读注册表（`:521`）、条件提交（`:537`）。两请求同时通过预检后，注册重试只查 UUID，同名仍可共存。窗口至少一次对象存储往返，按 P2 处理，修复在注册表条件提交重试内复核同列名称唯一性。

### 2.4 第 4 条：接受 P1，且仓库文档与实现已经矛盾

`docs/2026-11-21-parquet-to-iceberg-wrapping.md` 的"读路径"一节明确写"建索引时 parquet 由 Spark 自己的 reader 按列名读取……查询回表走 Iceberg Spark scan，靠 name mapping"。`3ba522674b` 之后回表改走格式模型且不传名称映射，文档描述的能力被破坏。修复时同步更新该文档的读路径描述。
