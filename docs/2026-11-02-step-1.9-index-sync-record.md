## 2. 一处前提修正：记忆模型其实不在 `main`

卡面原先写"`main` 已有 2780 系列记忆模型提交（`98222add3` 等），因此 `4015aba1e` 视为已有"。核对后这条不成立：

- `main` 的 `IndexCacheProtocol` 没有 charge version、没有 metadata shape；`ExecutorIndexCache` 1502 行，而 pin 上 2575 行；
- `IndexCacheMetadata`、`TestIndexCacheOwnedProtocol`、`TestIndexCacheReadContext`、`TestDistributedIndexSearchLoad`、`TestDistributedIndexSearchPreparedBytes` 只存在于基线分支；
- `main` 上的 `98222add3` / `bfdf75abe` / `3b1902142` 是 10 月 23–27 日的第一版驻留工作，不是 model 2 的"自有缓存元数据"。

也就是说，此前已落在 `main` 上的 model 2 估计（`5de488969`）和原地读取（`587dab47b`、`5ee0bb8d9`）缺少它们依赖的主干。修正办法不是把 1.9 形状的 `4015aba1e`（7262 行）硬解到 1.12，而是合并 `card/2773-merge`——同一份工作在 1.12 API 上原生写成的 28 个提交（含 6 个此前已逐个搬过的等价提交）。合并提交 `274997df2`，8 个文件冲突，解法是"保留本分支更新的那一侧，主干语义取 2773-merge"：

- Ivf/HNSW/FLAT kernel、`VectorMemoryEstimates`、模型计划文档：保留本分支较新的载荷计数上界、字典长度上界、共享 `JvmLayout` 探测；
- `IndexResidencyCoordinator.reportsFor`：保留基线的 stale-node 跳过（`4ddd13568`），其余交给 `node.projected(planId)`；
- 两个合并残留的旧调用点改为基线形状。

## 8. 已知问题与后续

1. `TestVectorIndexSearchBatch.cachedBatchSearchAppliesDeletes`：查询只取 k 条时，两条命中距离完全相等，最终次序由文件处理顺序决定，缓存与不缓存两次运行可能互换。单独运行通过，整批运行偶发失败。基线同样失败（testhive、spark_catalog）。
2. `scalastyleMainCheck`：索引 Scala 文件的既有格式债，需要在另一张卡上一次性修掉，否则 `main` 的 `build` 不能全绿。
3. 三条 `main` 侧修正（§5 的 `95d246c7c`、`102b41de2`）对应基线同样存在的缺陷，需要回搬 `step-1.9-index`，否则两条线会在"未覆盖文件里维度不一致的行"和"缓存状态可见性"上继续分叉。
4. 未推送：本次只做本地分支收口，`push` 到 GitHub 需单独授权。
