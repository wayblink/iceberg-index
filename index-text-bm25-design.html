BM25 文本索引方案（第二个索引类型）

在通用 index 层与 vector adapter 之上，设计第二个索引类型：BM25 全文检索索引。目的是用一类与向量本质不同的索引（语料级统计、字符串列、搜索需跨文件归约）验证通用模型是否需要新概念；结论是只需两个小扩展（关联搜索、行值编码），其余契约全部复用，且增量刷新不受影响。本文给出设计、决策、备选方案与实施计划。

阅读口径 复用：IndexMetadata / IndexSnapshot / IndexManifest(List) / IndexFile / IndexEntry / IndexQuery / IndexReader 全部不变。 新增：关联搜索 searchesAllPayloadsTogether() + searchAll/searchAuxiliaryAll、行值编码 encodeEntryValue(Object) 两个 core 扩展点。 新模块：iceberg-index-text（纯 Java，不引 Lucene），core 保持零算法依赖。 状态：已实现（core 关联搜索扩展 / index-text 模块 / Spark 通用索引构建 / SQL 过程与 list_indexes 泛化），向量检索行为经回归验证不变。 更新时间：2026-09-20

一、BM25 索引里到底存什么

BM25 是文本相关性排序函数。对查询 q 和文档 d：

组成内容作用
词项词典 + 倒排记录term → [(docId, tf)]查询词命中的候选文档及词频
文档长度表docId → |d|（词数）长度归一化
语料统计N（文档数）、总词数 → avgdl；每 term 的 dfIDF 与长度归一化都依赖全语料
行引用映射docId → (data_file, pos)把打分结果解析回表行（与向量索引同一锚点）
计分公式

BM25

score(q,d) = Σt∈q IDF(t) · f(t,d)·(k1+1) / (f(t,d) + k1·(1 − b + b·|d|/avgdl))，其中 IDF(t) = ln(1 + (N − df(t) + 0.5)/(df(t) + 0.5))（Lucene 式，保证非负）。k1 默认 1.2 控制词频饱和，b 默认 0.75 控制长度归一化强度。

分词

MVP 分析器

小写化 → 按非字母数字边界切分 → 丢弃短于 min-token-length（默认 2）的词 → 可选停用词表。不做词干化与同义词（留作后续）。查询与文档用同一分析器，保证 term 对齐。

二、与向量索引的本质差异（为什么这是好测试）

维度vector（EXACT / HNSW）text（BM25）
列类型array<float> / array<double>string
查询编码float[] 向量文本字符串（分词在 adapter 内）
索引结构每数据文件一份：entries 或 HNSW 图每数据文件一份：局部倒排记录 + 局部统计头（多对一分组后同构，见 D18）
打分依赖行内（两个向量的距离）语料级统计（df、avgdl 全局量，搜索时跨文件归约）
搜索输入逐个 index 文件独立搜索后合并需要同时看到全部 index 文件（先合并统计再打分）
增量刷新文件级 diff，未变文件复用同样文件级 diff：局部统计不变，全局统计搜索时自动反映变化
排序方向距离升序 / 相似度降序相似度降序（同 COSINE/DOT）
索引文件 kindENTRY_BEARING 或 AUXILIARYAUXILIARY（HNSW 同类）

结论先行：除“整表粒度”与“行值编码”两点外，现有契约无需改动——这正是本方案要验证的命题。

三、设计决策

已定型结论
D10 · 关联搜索core IndexAdapter 增加 default boolean searchesAllPayloadsTogether()（默认 false）与 searchAll / searchAuxiliaryAll（默认实现=逐文件搜索后合并，与现状等价）。text adapter 覆写为 true：reader 收集同 kind 的全部 payload 交给 adapter，adapter 先合并各文件的局部统计（df/N/totalLen → 全局 df/avgdl）再打分。索引文件粒度保持每数据文件一个，coverage / refresh / 血缘 / 删除语义全部不变，增量刷新天然成立
D11 · 行值编码core IndexAdapter 增加 default byte[] encodeEntryValue(Object columnValue)：入参是引擎给出的列值自然表示（数值数组列 → List<Number>，文本列 → String）。Spark 侧只保留一条通用 entries 读取管线（含删除应用），不再按索引类型分派；新 adapter 零 Spark 改动
D12 · 查询载荷沿用 IndexQuery.payload() 为 ByteBuffer：向量 = float 字节，文本 = UTF-8 字符串；分词与编码都在 adapter 内完成，core 不感知
D13 · 模块放置新模块 iceberg-index-text（包 org.apache.iceberg.index.text），与 index-vector 对称；BM25 打分与分词自行实现，不引 Lucene，core 保持零算法依赖
D14 · BM25 参数definition 参数：field-id、k1（1.2）、b（0.75）、min-token-length（2）、lowercase（true）、stopwords（可选）、properties。IDF 采用 Lucene 式 ln(1 + (N−df+0.5)/(df+0.5))
D15 · blob 格式每数据文件一个版本化二进制：magic + version + k1/b + 局部统计头（本文件 N、totalLen、各 term 的 df_local）+ 局部 term 词典与 postings（docId 用文件内行号）+ docId→(file,pos,长度) 表；blob type iceberg-text-bm25-v1（AUXILIARY kind）；entry-bearing blob type 名义保留 iceberg-text-entries-v1（不使用）
D16 · 刷新语义与 vector 完全一致：数据文件增删或适用 delete 文件变化 → 只重写受影响的 index 文件（局部 postings 与局部统计头随之更新），未变文件按父快照血缘复用；无变化 → no-op。全局统计不在索引文件里落地，而在搜索时由各文件局部统计归约得出，因此无需全量重建
D17 · SQL 入口与 vector 对称新增 build_text_index / refresh_text_index / text_search；list_vector_indexes 泛化为 list_indexes（schema 增加 definition JSON 列，去掉 vector 专列）。泛化为 build_index(type, options) 的统一面留作后续
D18 · 索引文件分组本期约束仍是一对一（一个数据文件 → 一个 index 文件），但模型已支持多对一：IndexFile.coveredDataFiles 本就是列表，coverage/uncovered/删除语义都按集合运算。多对一（按分区 / 按大小预算 / 整表建大索引）列为后续扩展点，构建侧以分组策略承载，不做模型改动（详见第九节）

四、关键决策的备选方案与取舍

D10 核心问题

构建可分区，计分必须全局

倒排记录可按数据文件（或任意范围）并行构建；df(t)=Σ 分区 df_local、avgdl=Σ totalLen / Σ N 都是可加和，可归约。唯一不可分区的是计分：单文档分数依赖全局 df 与 avgdl。因此设计问题是“全局统计在哪里合并”——Lucene 的答案是查询时按 segment 合并，本方案同此。

D10 备选 A

整表单文件（初版方案，已否决）

构建后在驱动端合并所有 entries，写一个覆盖全表的 index 文件（isTableWide()）。否决原因：任何数据变化都使全局统计过期 → 增量刷新失效，只能全量重建；驱动端聚合全部 entries 有内存压力；SparkIndexBuilder 需要特殊的 table-wide 分支。

D10 备选 B

每文件内嵌全局统计副本

每个 index 文件除局部 postings 外内嵌同一份全局统计，搜索时逐文件独立打分。否决原因：与 A 一样任何变化都使全部副本过期，刷新仍要重写全部文件，却比 A 多写 N 倍、多读 N 份统计。

D10 选定

局部 postings + 查询时归约

每个 index 文件 = 局部 postings + 局部统计头（本文件的 N、totalLen、各 term 的 df_local）；reader 在 searchesAllPayloadsTogether()=true 时把全部 payload 交给 adapter，adapter 合并统计头得到全局值后打分。收益：文件级增量刷新原样可用、构建复用每文件并行管线、无驱动端聚合。代价：reader 多一个分支；该路径需同时持有全部 payload（BM25 本就需要全量 postings 找候选；vector/HNSW 走默认路径不受影响）。

D11 备选

为什么不在 Spark 侧分派

备选：Spark 侧按 definition 类型选择 entries 读取器（VectorIndexEntries / TextIndexEntries）。否：每新增一个 adapter 都要改 Spark 模块，违背“engine 中立 + adapter 可插拔”的目标；Object 入参的松散性用 javadoc 约定（List<Number> / String）约束，是可接受的代价。

D13 备选

为什么不引 Lucene

Lucene 的 BM25Scorer 与分析器链更完整，但依赖重、索引格式要落盘兼容。否：MVP 自实现计分与分词（约 300 行），blob 格式自主可控；后续如需更复杂分析（词干化、CJK）再评估。

五、正确性契约的继承与变化

契约text 索引的继承/变化
① 身份不变：table-uuid + sidecar 目录
② 绑定不变：绑定 source-table-snapshot-id；血缘校验（回滚后拒绝 refresh）同样适用
③ 覆盖每个 index 文件覆盖它构建时读取的数据文件；全部覆盖则 uncoveredDataFiles 为空（与 vector 同）
④ 锚定不变：docId → (data_file, pos)，pos 为数据文件内原始行序号
④-A 删除语义复用同一条管线：entries 读取应用该快照的 position/equality delete，被删文档不进索引、不出现在查询结果
⑤-A 孤儿清理不变：整表索引刷新后旧文件被父快照引用期间保留，父快照过期后由 cleanup 过程删除
刷新与 vector 相同：文件级 diff，只重写受影响数据文件的 index 文件；全局统计不在索引内落地，故无需全量重建

六、测试策略

单元

index-text 模块

分词（大小写/标点/停用词/最小长度）；BM25 打分与测试内手算公式逐项对齐（小语料、可手算 IDF 与 tf 归一化）；encodeAuxiliaryPayload → searchAuxiliary round-trip；definition JSON round-trip（经 IndexMetadataParser）。

集成

Spark SQL 端到端

建表灌文本 → build_text_index → text_search 排序与参考实现一致 → DELETE 行后 refresh，被删文档不再出现 → 新文档可搜到。覆盖四种 catalog 参数化。

回归

不破坏 vector

SIFT 端到端 recall 不变（EXACT 1.0 / HNSW 0.994）；既有 vector 过程、删除、清理、批量测试全绿；core 测试不减。

七、已知限制（诚实列出）

限制影响后续
关联搜索路径需同时持有全部 index 文件 payload超大表时 reader 端内存；vector/HNSW 走默认逐文件路径不受影响两趟式：先读各文件统计头合并，再逐文件流式打分（需 reader 支持懒加载 payload）
分词简单（无词干化/CJK/同义词）召回质量受限分析器可配置化；评估 ICU/CJK 分词
查询词权重统一（无 per-term boost）表达力受限查询编码支持 term:weight
text_search 行解析逐文件读 parquet单查询成本同 vector 优化前复用已实现的批量解析路径（VectorIndexSearch 泛化）
本期一个数据文件对应一个 index 文件，数据文件多时 index 文件数膨胀、查询归约对象多文件数与管理开销；BM25 归约对象多多对一分组（D18，模型已就绪，仅需构建期分组策略）

需要你确认的点

① D10′ 关联搜索（每文件局部 postings + 查询时归约统计）是否认可，替代初版的整表单文件方案；② D11 的 encodeEntryValue(Object) Object 入参是否认可（javadoc 约定 List<Number> / String）；③ D17 SQL 面先做 text 专有过程（低变更，推荐）还是直接泛化 build_index(type, options)。

九、索引文件分组：多数据文件 → 一个索引文件（本期不做，模型已就绪）

对更多数据构建大索引往往性能更好：BM25 的 postings 越大，查询时归约的对象越少、局部性越好；HNSW 的图越大，越接近全局最近邻，可消除跨文件 top-k 合并造成的召回损失。当前“一个数据文件对应一个索引文件”只是构建期的分组策略，不是模型限制。

模型就绪度

IndexFile.coveredDataFiles 从设计上就是列表，IndexManifest.indexedDataFiles()、覆盖差集、删除语义、血缘与孤儿清理全部按集合运算——多对一无需任何模型改动，只改构建期的分组决策。

机制一对多（本期）多对一（后续）
数据模型coveredDataFiles 单元素不变：列表多元素；entry 各自带自己的 data_file + pos
构建repartition by data_file，每文件一个 index 文件分组策略（按分区 / 按字节数预算 / 整表）决定哪些数据文件的 entries 进同一个 index 文件；entries 生成与删除应用不变，分组发生在其后
刷新文件级 diff，只重写受影响数据文件的 index 文件重建粒度变粗：任一被覆盖数据文件变化 → 重写整个 index 文件（重新读取它覆盖的全部数据文件）。分组越大增量越贵，需在策略中权衡（大表可配“按分区分组 + 分区级重建”）
BM25 统计归约每 index 文件一份局部统计头，搜索时跨文件合并正交且兼容：分组只改变每个 index 文件覆盖多少文档，归约仍是可加和；文件更少则归约对象更少
HNSW 图每文件一个图，跨文件合并 top-k更大图 → 更高召回（消除合并损失）；刷新代价同上升
覆盖检查uncoveredDataFiles 差集不变（集合运算）

扩展点预埋：构建请求（IndexBuildRequest）后续增加分组/大小预算参数；Spark 侧把 repartition 键从 data_file 换成分组键。本期实现保持一对一，不预做策略，但所有契约按多对一兼容的方式书写。

设计依据：通用 index 层数据模型（index-data-model.html）的四级文件结构与横切契约；vector adapter（index-vector）作为第一个适配器的实现经验。本文只覆盖 BM25 文本索引类型，不改变已定型的核心契约。
