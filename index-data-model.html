Apache Iceberg · Index Data Model

Index 层数据模型设计

在 vector MVP 与两份拓扑图之上，给出 index 层的对象模型：完全仿照 Iceberg 数据层的四级文件结构，用四条横切契约把派生索引安全地绑定到表元数据上。本文只聚焦数据模型与关系，不涉及构建执行与引擎接入细节。

阅读口径 结构同构：IndexSnapshot : IndexManifestList : IndexManifest : IndexFile ≡ Snapshot : ManifestList : Manifest : DataFile。 语义不同构：index 是绑定在表快照上的派生投影，不是权威。 已定型：四级物理文件 / parent-index-snapshot-id / IndexFile 单类 + kind。 更新时间：2026-09-18

结论先看

Index 层的数据模型完全仿照 Iceberg 数据层：IndexMetadata 为根，向下经 IndexSnapshot → IndexManifestList → IndexManifest → IndexFile 四级落到 IndexEntry。结构与数据层一一对应，用户对 snapshot / manifest 的全部直觉可以直接迁移；但 index 是派生层，必须靠四条横切契约（身份、绑定、覆盖、锚定）保证与表元数据的一致性和正确性。

本次定型的三件事

① v1 直接落四个物理文件，不合并中间级；② IndexSnapshot 增加 parent-index-snapshot-id，镜像表快照血缘，支撑增量 refresh；③ IndexFile 单类 + kind 字段，LeafFile 降级为 payload 种类。

一、与数据层的结构同构

Iceberg 数据层对象（已有） Index 层对象（新增） 跨层契约（绑定 / 覆盖 / 锚定）

结构同构、语义不同构：index 层四级完全镜像数据层，IndexSnapshot 额外携带 source 绑定与 parent 血缘；虚线是派生层的三条横切绑定（身份、版本、覆盖 / 锚定）。

三、Index 与 Table Meta 的关系契约

结构可以镜像，语义必须划清边界。index 层对数据层只有四条横切契约，全部正确性规则都从这四条推导。

总原则

表快照永远是权威；index 快照只对它绑定的那个表快照有效，且只覆盖它构建时实际处理的文件。

契约 ① · 身份

只认 table-uuid

IndexMetadata 通过 table-uuid 关联表，不用表名——表改名不影响索引归属；冗余 table-location 仅用于解析。MVP 阶段 index 是 sidecar 实体，模型按未来可平移进 TableMetadata / REST Catalog 设计。

契约 ② · 绑定

只对 source-table-snapshot-id 有效

每个 IndexSnapshot 绑定一个表快照。planner 第一步校验当前表快照与 index 快照绑定是否一致：不匹配则 refresh 或 fallback，绝不默认“有索引就全表安全”。发布时校验 parent 的 source 是本 source 的祖先——已实现：SparkIndexBuilder 在 refresh 时要求新 source 表快照是最新 index 快照所绑定快照的后代（表回滚后从旧快照 refresh 会静默丢数据，直接拒绝），build 时校验 source 表快照存在。

契约 ③ · 覆盖

覆盖是部分且可选的状态

IndexManifest 记录 covered data files；planner 将其与绑定表快照 manifest list 中的 live files 做差集，未覆盖文件走 residual scan。数据层的 manifest list 按定义完整，index 层的覆盖只是构建期的部分断言。

契约 ④ · 锚定

_file + _pos 回表

IndexEntry 持有 data-file path + row position，与 manifest entry 的锚点一致，任何引擎都能把索引结果解析回表行。重写改变文件路径 → 覆盖失效 → refresh。

契约 ④-A · 删除语义

index 快照 ≡ 表快照（含删除）

构建/refresh 时应用删除：position delete 文件删除的位置、equality delete 文件匹配的行，都不进索引；记录的 position 是数据文件内的原始行序号（即 _pos）。这样索引结果对绑定快照就是“全活行”，查询无需再应用删除。已实现：VectorIndexEntries 读数据文件为 parquet 并应用该快照的 delete files；refresh 除数据文件增删外，还重建“适用 delete 文件集合发生变化”的数据文件的索引。未实现（后置）：查询期兜底应用删除、delete 文件自身的过期协调。

契约 ⑤-A · 孤儿清理

只删不被存活快照引用的文件

索引树 <table-location>/indexes/<uuid>/ 下 data/ 与 snapshots/ 中不被任何存活 index 快照引用的文件即孤儿：包括被 refresh 丢弃文件的旧快照过期后的文件、失败构建的残留。已实现：CALL cleanup_vector_index_files——先按“绑定的表快照已过期”丢弃 index 快照前缀（新首快照 parent 置空以保持血缘合法），再删除不被存活快照引用的文件，返回过期快照数 / 删除文件数 / 字节数；registry 与 metadata 文件永不受影响。清理期间不得有构建/refresh 在飞。

契约 ⑤ · 生命周期

retention 让位于表快照过期

表快照过期后，绑定它的 index 快照应同步清理；leaf 文件只有在不被任何存活 index 快照引用时才是孤儿。判断依赖 parent-index-snapshot-id 链 + 各 manifest 的文件引用（见第四节）。保留策略首版：丢弃“绑定表快照已不存在”的 index 快照前缀（保持血缘连续，新首快照 parent 置空），由 cleanup_vector_index_files 过程执行（见契约 ⑤-A）。

四、IndexSnapshot 的语义与 parent-index-snapshot-id

IndexSnapshot 是什么

IndexSnapshot 是 index 层对应表 Snapshot 的“某一时刻的不可变状态”，但有一个根本差别：表快照是权威状态本身，IndexSnapshot 是派生构建。它回答的问题是：“针对表快照 S，这个索引在某个时间点构建出来、当时被判定为可用的那一版索引是什么。”每个字段只承担一种职责。

与代码注解同步

本节语义已同步写入 VectorIndexSnapshot 的类注释；泛化重构时随类迁移到 IndexSnapshot。

字段职责说明
snapshot-id身份index 快照自身标识，index 范围内唯一
source-table-snapshot-id绑定构建所依据的表快照；IndexSnapshot 只对它有效（契约 ②）
parent-index-snapshot-id血缘派生来源；全量重建时为 null

不变式：① 一个 Index 对同一 source-table-snapshot-id 至多有一个 IndexSnapshot（MVP 沿用现有约束）；② parent 为 null，或 parent 的 source 表快照是本快照 source 的祖先；③ status = PUBLISHED 才可被 reader / planner 使用；④ IndexSnapshot 及其文件层全部不可变，变化只能通过发布新快照表达。

parent-index-snapshot-id：血缘链与增量 refresh

IndexSnapshot.parent-index-snapshot-id 记录“本快照从哪一个 IndexSnapshot 派生而来”，完全镜像表快照的 parent-snapshot-id。它服务四件事：增量 refresh 的复用基础、血缘可审计、compaction 的作用域、retention 与孤儿清理的安全判断。

关键区别

index 链不必与表链 1:1：表 S1→S2→S3，index 可跳过 S2 直接为 S3 构建。diff 用表链算，复用用 index 链——表链回答“数据发生了什么变化”，index 链回答“哪些既有索引文件可以接着用”。

步骤动作依据
1取当前 index tip I(S1) 作为 parentIndexMetadata.snapshots
2沿表链计算 diff(S1 → S2)：added / removed / rewritten data files、新增 delete files表 manifest list
3复用 parent 中覆盖未变文件的 leaf；丢弃覆盖被删 / 重写文件的 leafparent 的 IndexManifestList
4仅为 added / changed 文件构建新 leaf，写入 attempt 作用域路径IndexBuilder
5写 IndexManifestList / IndexManifest / IndexFile文件层（见第七节）
6原子更新 IndexMetadata：追加 IndexSnapshot(id, source=S2, parent=I(S1), status=PUBLISHED)发布协议（见第七节）
7失败则丢弃 attempt 文件；成功后 parent 中被完全放弃的 leaf 进入孤儿清理候选IndexLifecycle

边界规则：全量重建时 parent = null；发布时校验 parent 的 source 表快照必须是本快照 source 的祖先；并发 refresh 后到者竞争 IndexMetadata 更新，失败方丢弃 attempt 文件。

五、IndexFile 与 kind 字段

模型里只有 IndexFile 一个文件类（≡ DataFile 的对应物），LeafFile 不再是层级概念，降级为 payload 种类。理由是：将来的 ANN 索引需要非 entry 承载文件（HNSW 层间图、IVF coarse quantizer、bloom sidecar），它们都是 IndexFile，但不是 leaf。

对现状的影响

现有 VectorIndexLeafFile 重概念化为“kind = entry-bearing 的 vector IndexFile”，payload 格式记作 vector-entries-v1；reader 的“返回行引用”能力只对 entry-bearing 文件成立。

kindpayload 内容状态
entry-bearing行引用（_file + _pos）+ 值（float[] / 键值）当前：vector-entries-v1（即现 VectorIndexLeafFile）
auxiliary图结构 / 量化器 / 统计未来：HNSW upper layers、IVF coarse quantizer 等

七、发布协议与文件布局

发布协议与表快照提交同构：先写文件、后原子切根。任何读者在 IndexMetadata 更新前都看不到新 index 快照。

容器选型（已定 D8）

IndexFile 统一采用 Puffin 容器：MVP 二进制编码原样进 blob（blob type = iceberg-vector-entries-v1），类型参数写入 blob 元数据。容器接口可插拔，Puffin 为首选实现；元数据模型不变。

<index-location>/ metadata/ index-metadata-v1.json # IndexMetadata 根（原子发布点） snapshots/ index-manifest-list-<idx-snap-id>-<uuid>.bin index-manifest-<idx-snap-id>-<seq>-<uuid>.bin data/ index-file-<idx-snap-id>-<seq>-<uuid>.puffin staging/ <attempt-id>/f0, f1, ... # attempt 台账（写前日志），失败即弃 metadata/ index-metadata-pointer-0.json # 指向当前 metadata 版本（双槽轮转）

协议：① 每个文件写入前先在 staging/<attempt-id>/ 登记一个 marker（写前日志，marker 从 0 顺序编号，无目录列表也可枚举）；② 写最终路径；③ 写 manifest / manifest-list；④ 写 complete marker，随后原子更新 IndexMetadata（新版本文件 index-metadata-v1-g<N>.json + 指针切换，仿表 metadata 提交）；⑤ ④ 成功前读者不可见新快照；进程内失败调 abortAttempt 精确删除台账登记的全部路径；进程被杀则台账留在原地，由 cleanup_index_files 按台账清理（executor 直接写的索引文件另有未引用文件清扫兜底）。

附：快速开始——MVP 通路
