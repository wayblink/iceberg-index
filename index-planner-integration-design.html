索引层 Planner 集成方案方案待评审 · 本期不动代码

范围：让 SELECT ... ORDER BY <distance> LIMIT k 与文本检索查询自动走索引，而不必显式 CALL。 前置：索引层核心、向量/BM25 两类适配器、SQL 过程面、原子发布与 attempt 台账、1:N 分组均已落地。

结论先行

分两步走：第一步做 TVF（表值函数），把已成熟的 CALL 通路包成可出现在 FROM 子句里的函数， 用户写 SELECT * FROM vector_index_search(t, 'embedding', array(...), 10)，planner 只做“解析 + 展开成物理读取”， 不碰代价模型，工作量小、无正确性风险。第二步再做 rule-based 自动改写：识别 ORDER BY distance LIMIT k 形态并替换为索引扫描 + 残差扫描，需要距离表达式、规则与统计信息三件套，风险和工作量都大得多。

一、现状与缺口

目前索引只能通过过程调用：

CALL spark_catalog.system.vector_search(
    table => 'db.docs', column => 'embedding', query => array(0.95d, 0.05d), k => 10);

它返回 data_file / pos / score / row(JSON)。三个缺口：

  1. 不可组合：结果是一张扁平的 JSON 字符串列，不能再 WHERE、再 JOIN、不能只取部分列（列被序列化进 JSON）。
  2. 不自动：用户必须知道索引存在并显式调用；写 ORDER BY ... LIMIT 10 时不会走索引。
  3. 无类型化契约：距离/相似度在 core 里是适配器内部实现（VectorIndexAdapter.encodeQuery + resultComparator）， planner 无法知道 vec_distance(embedding, q) 与该索引是同一回事。

二、第一步：TVF（表值函数）

2.1 形态

-- 向量
SELECT * FROM vector_index_search(
    table => 'db.docs', column => 'embedding',
    query => array(0.95d, 0.05d), k => 10);

-- 批量向量（一次多查询）
SELECT * FROM vector_index_search_batch(
    table => 'db.docs', column => 'embedding',
    queries => array('0.95,0.05', '0.1,0.9'), k => 10);

-- 文本
SELECT * FROM text_index_search(
    table => 'db.docs', column => 'body', query => 'iceberg table format', k => 10);

输出保持现有过程 schema（data_file / pos / score / row），因此实现是“把过程逻辑搬到 TVF”。

2.2 落点

项内容
实现位置spark/v3.5/spark-extensions（与过程同模块，均依赖 iceberg-spark + iceberg-index-vector/text）
入口IcebergSparkSessionExtensions.injectFunction
实现方式实现 Spark 的 TableValuedFunction（Scala），内部直接调用已存在的 VectorIndexSearch / IndexSearch / TextIndexAdapter
解析TVF 由 Spark 原生语法支持（FROM name(args)），无需自定义 parser

2.3 为什么这一步安全

  • 不改变任何查询的语义：只有显式写 TVF 的查询才会走索引，等价于今天的显式 CALL。
  • 不碰 optimizer：没有新规则、没有代价模型、没有统计信息依赖，回归面就是“过程还能用”。
  • 核心逻辑零改动：driver 侧检索 + 每命中数据文件读一次，已经是现成代码。

2.4 已知限制（本期接受）

  • row 仍是 JSON 字符串。要变成类型化列需要“按索引结果回表”的物理算子（见 3.4），留到第二步。
  • 只支持 Spark 3.5（TVF 的参数传递方式在 Spark 3.4/3.5/4.x 之间有差异，4.1 已不在维护范围）。

三、第二步：rule-based 自动改写

3.1 目标形态

-- 用户只写普通 SQL
SELECT id, body FROM db.docs
ORDER BY vec_distance(embedding, array(0.95d, 0.05d)) LIMIT 10;

-- 文本
SELECT id, body FROM db.docs
WHERE body MATCH 'iceberg table format' LIMIT 10;   -- 或 text_score(body, '...') > 0

3.2 需要的三件套

组成内容难点
① 距离/相关度表达式vec_distance(col, query)（返回 double，语义由索引的 metric 决定）、text_score(col, query)（BM25 分数）表达式的语义必须与索引一致：同一列上不同 metric 的索引给出不同距离，表达式要知道用哪一个
② optimizer 规则识别 Sort(distance, Limit k) / Filter(text_score > t) 形态，查找该列可用索引，替换为“索引扫描 + 残差扫描”何时相信索引：必须校验索引快照绑定的表快照与当前读快照的关系（IndexQuery.Consistency 已就绪），否则要回退全表扫描
③ 物理执行索引扫描在 driver 侧完成（现成），命中行需要按 _file/_pos 回表取列，并做残差扫描补齐索引未覆盖的数据文件回表要避免全量 shuffle；残差扫描与索引结果的合并/去重/再排序

3.3 索引选取与一致性

planner 规则输入：Project/Filter/Sort/Limit + IcebergScan(表, 读快照 S) │ ├─ 提取检索列 c 与查询载荷 q（距离表达式常量参数 / MATCH 字面量） ├─ IndexCatalog.listIndexes(table.location()) │ └─ 选 definition.fieldId == c.fieldId 的索引；同列多个索引时按 index_type 匹配表达式类型 ├─ 一致性判定（core 已提供两种模式） │ ├─ EXACT_SNAPSHOT：索引快照绑定的表快照 == S → 直接用，无残差 │ └─ AT_OR_BEFORE：取绑定快照 ≤ S 的最新索引快照 → 需 uncoveredDataFiles 残差扫描 └─ 都不满足 → 不改写（回退全表扫描），并可按需提示用户 refresh

索引快照与表快照的绑定关系是这条链路的正确性基石，已在 core 落实（IndexSnapshot.sourceTableSnapshotId + 发布时的血缘校验）。

3.4 物理计划草图

VectorIndexSearchExec(k, q)                 -- driver 侧检索，产出 (data_file, pos, score)
        │
        ├─ IndexedRowsLookup(data_file, pos) -- 按命中位置回表取所需列（每文件一次读）
        │
        └─ ResidualScan(uncoveredFiles)      -- 索引未覆盖的数据文件，普通扫描 + 同样排序
                 │
                 └─ Union + Dedup + TopK(k)  -- 合并两侧结果，取全局前 k

向量侧还要处理：精确重排。HNSW 是近似检索，索引返回的候选必须用原始向量重算距离再取 top-k （core 的 VectorIndexAdapter 已实现“索引粗排 + 精确重排”，planner 只需保证重排发生在回表之后）。

3.5 文本侧差异

  • 没有“排序取 top-k”的自然形态，更自然的入口是 WHERE text_score(body, 'q') > 0 ORDER BY text_score DESC LIMIT k， 规则要同时识别 Filter 与 Sort。
  • BM25 分数依赖全库统计（N、avgdl），索引文件里存的是本地统计、查询时合并（D10′）。 若索引快照落后于读快照，合并出的 df/avgdl 与全表真实值有偏差，分数仍可用于排序，但绝对值不再精确—— 这一点必须写进文档，并在 AT_OR_BEFORE 模式下考虑是否仍自动启用（建议：文本默认要求 EXACT_SNAPSHOT）。

四、分期与验收

阶段内容验收风险
P1 · TVF3 个 TVF（vector / vector_batch / text），复用现成检索与行解析与对应 CALL 结果逐行一致；可嵌套子查询/过滤/join低
P2 · 表达式 + 规则骨架vec_distance 表达式；规则只处理 Sort+Limit，且仅 EXACT_SNAPSHOT 命中时改写EXACT 命中时结果与全表扫描一致；未命中时计划与今天完全相同（可断言 explain 输出）中
P3 · 残差与回表AT_OR_BEFORE + uncoveredDataFiles 残差扫描 + 类型化回表列索引落后时结果与全表扫描一致（SIFT 数据集 recall/正确性对齐）中高
P4 · 文本与 HNSW 重排text_score 形态；HNSW 候选精确重排BM25 排序与 brute-force 对齐；HNSW recall 与直连过程一致中

五、决策点（待确认）

  1. P1 是否单独先上？ TVF 与过程并存，不改变任何现有行为，可作为“可组合入口”独立交付。
  2. 距离表达式归属：vec_distance 放在 spark-extensions（Iceberg 侧）还是等 Spark 官方 ML 函数？建议前者，语义与索引 metric 绑定，官方函数无法感知索引。
  3. 索引落后时是否自动启用：向量建议允许 AT_OR_BEFORE + 残差扫描；文本建议默认只走 EXACT_SNAPSHOT（统计合并偏差）。
  4. 同列多索引的选择策略：按 index_type 匹配表达式；同类型多个索引（如同一列两个 metric）建议报错提示用户显式指定，避免猜错 metric。
  5. 未命中索引时是否提示：可在规则里打点/告警（“该查询形态可用索引但索引快照落后”），但不改变计划。

六、检索的分布式化（driver 不是执行点）

索引检索最初跑在 driver 上：规则在规划期调 IndexReader.search()，顺序读每个索引文件的 payload 并逐文件打分。 三个调用点（改写规则、批量检索、各过程）全都如此。量级一大就是瓶颈——EXACT 模式 100 万条 × 768 维的单次查询约 1.5 GFLOP， driver 单线程跑一秒多，批量 100 个查询就是 150 秒；读取顺序、计算串行、单个 payload 常驻 driver 堆。

现已改为 executor 侧执行（DistributedIndexSearch），并把归约也改成分布式：

阶段在哪做什么driver 上的量
解析索引快照driver读 manifest list + manifests，得到索引文件位置列表（IndexReader.indexFiles(query)）小：清单本身
本地 top-kexecutor每个索引文件整体读入（文件永不拆分），解 Puffin 容器，取 adapter 对应的 blob，逐文件搜索，只留该文件最好的 topK+1 个0
全局归约executor树形 takeOrdered：各 task 的局部 top-k 逐级合并，最终只回传 topK 个0（只有最终 topK 回到 driver）
回表executor按命中位置读数据行，删除感知0

分区不是字节问题，是单位问题。曾用 spark.read.format("binaryFile") 读索引文件， 但其分区由 maxPartitionBytes（默认 128MB）+ openCostInBytes（默认 4MB，小文件也按此计） + minPartitionNum（默认集群核数）共同决定，与索引文件的语义边界无关（TestBinaryFilePartitioning 钉住了这套行为， 也钉住了 per-read 的 maxPartitionBytes 选项对 binaryFile 不生效）。并行度实际是 max(按大小打包的分区数, 集群核数) 且不超过文件数。

归约的顺序是 SPI 契约。分布式归约只能在 task 间传「分数 + 行引用」三个值， 所以 IndexAdapter.resultComparator() 被明确为契约：按分数排序（距离升序、相似度降序）， 平分按数据文件名再按行位置。引擎侧用两个仅分数不同的结果探测分数方向，然后自行应用平分规则。 TestDistributedIndexSearch 用 12 个索引文件、跨文件平分、topK ∈ {1,3,5,12} 对齐 brute-force， 并对「去掉平分」和「反转分数方向」两个变异均报警。

还剩一件事：改写方案本身要求最终 ≤ limit 行回到 driver。规则用 LocalRelation 替换扫描叶节点， 这是规划期物化，所以 top-k 的最终结果必须落在 driver 上（量被 topK 限制，可接受）。 要彻底不让 driver 沾数据，需把索引检索做成 Iceberg BatchScan：执行期才跑、分布式、不落 driver。列为后续。

七、与既有设计的关系

既有能力在 planner 集成中的角色
IndexReader + IndexQuery.Consistency快照选取与一致性判定，规则直接复用
IndexReader.uncoveredDataFiles残差扫描的文件清单
VectorIndexSearch / IndexSearchdriver 侧检索与批量检索，TVF 与规则的共同底座

1:N 分组（D22）索引文件更少更大：并发行数更少，但单个 HNSW 图覆盖更多向量，召回更高（分片 ANN 的召回是分片级的）
